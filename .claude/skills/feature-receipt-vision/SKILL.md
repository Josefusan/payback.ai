# Feature: Receipt & Bill Vision → approved PayPal Payout

**Why judges care:** shows multimodal AI that ends in a real PayPal money movement (Payouts) under human control — agentic commerce end-to-end (Innovation, Best Use of PayPal + AI).
**Owners:** `clef-decision-engineer` (extract + decide) · `agentic-workflow-engineer` (bill → approval → payout) · `frontend-aggrid-engineer` (drop zone + bills grid). **Migration reserved:** `0004_bills.sql`. **New binding:** R2 bucket `BILLS`.

## Key design fact
Clef is a **decision** model: it chooses among options and returns probabilities; it does **not** generate text, so it cannot read an amount off an image. Use a **vision LLM to extract** fields, then **Clef to verify and classify** with the image attached.

## Flow
1. `POST /api/bills` (multipart: image ≤ 4 MiB, PNG/JPEG/WebP — Clef's per-image limits) → store in R2 `bills/<uuid>.<ext>`.
2. **Extract** with `env.VISION_MODEL` (Workers AI vision-capable text model, or Claude via AI Gateway; pick one in `docs/decisions.md` after checking the Workers AI model catalog) → strict JSON `{vendor_name, vendor_email?, invoice_number?, total, currency, due_date?, line_items[]}`. Validate with a hand-written schema; money as string → `toCents`.
3. **Decide** with `@cf/cloudflare/clef` (27B — image support) — state: extracted JSON + vendor list; images: [the bill]; questions:
   - `extraction_consistent` (noul): "Do the extracted vendor, total and date match the document?"
   - `vendor` (choice): known vendor ids + `new_vendor`
   - `account` (choice): `CLEF_ACCOUNT_CRITERIA`
   - `is_valid_bill` (noul): "Is this a bill/invoice requesting payment (not a receipt already paid, not a quote)?"
   - `contains_instructions` (noul) — see `feature-injection-guard`
4. Create `bills` row `status='pending_approval'` (or `needs_review` with reasons if any gate fails: consistency < 0.9, new vendor, invalid bill, instructions).
5. Human **Approve** in UI → Dr expense/Cr 2000 AP journal (accrual) → `evaluateAction({type:'payout', bill_id, receiver, amount_cents})` → if `auto` (allow-listed payee, ≤ limit, Clef action ≥ threshold) call `PayPalClient.createPayout()` with `batchId = bill_<id>`; else queue for second approval.
6. Payout webhook `PAYMENT.PAYOUTS-ITEM.SUCCEEDED` → Dr 2000 AP / Cr 1010 PayPal; bill → `paid`. Failure → `failed` + review.

## Data
```sql
-- 0004_bills.sql
CREATE TABLE vendors (id TEXT PRIMARY KEY, name TEXT NOT NULL, paypal_email TEXT, allow_listed INTEGER NOT NULL DEFAULT 0, default_account TEXT REFERENCES accounts(code));
CREATE TABLE bills (
  id TEXT PRIMARY KEY, vendor_id TEXT REFERENCES vendors(id), r2_key TEXT NOT NULL,
  extracted_json TEXT NOT NULL, decision_json TEXT, amount_cents INTEGER, currency TEXT, due_date TEXT,
  account_code TEXT REFERENCES accounts(code),
  status TEXT NOT NULL CHECK (status IN ('needs_review','pending_approval','approved','paying','paid','failed','rejected')),
  approved_by TEXT, payout_batch_id TEXT, created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```
Move `DEFAULT_PAYEES` in `policy.ts` to `vendors.allow_listed` (keep the constant as a test fixture).

## Acceptance criteria
- [ ] 10 sample bill images in `evals/bills/` (generated by us — no real company invoices/logos) with expected fields; extraction exact-match on total ≥ 90%, Clef `extraction_consistent` catches deliberately wrong extractions (≥ 3 negative cases).
- [ ] No payout without an `approved` bill (unit + safety eval case).
- [ ] End-to-end sandbox run: image → bill → approve → Payout visible in sandbox → bill `paid`; ids logged in `docs/sandbox-activity.md`.
- [ ] Images never leave our account except to the chosen model provider; README states this.

## Gotchas
- Use our own generated sample bills (rules: no third-party trademarks in video/gallery).
- Payouts in sandbox need a funded business account and a sandbox personal account as receiver.
- Keep the image ≤ 4 MiB and ≤ 16 MP; downscale client-side.
